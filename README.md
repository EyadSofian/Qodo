# مساحة عمل إنجوسوفت · Engosoft Workspace

**جميع تطبيقات الشركة في مكان واحد — شبكة أيقونات، مستخدمون وصلاحيات، ولوحة مهام لكل قسم.**

_One hub that launches, embeds and links every Engosoft app._

## ما هذا

بدلاً من رابط منفصل لكل لوحة وتسجيل دخول منفصل لكل واحدة، مساحة واحدة تضم:

- **شبكة تطبيقات** — كل تطبيق أيقونة، كشاشة الهاتف. تُفتح داخل المساحة أو في تبويب.
- **شريط علوي موحّد** — الشبكة والبحث والإشعارات متاحة في كل شاشة.
- **مستخدمون وصلاحيات** — أضف موظفاً، حدّد دوره وقسمه، وحدّد بدقة التطبيقات التي يراها.
- **لوحة مهام لكل قسم** — مراحل مختلفة لكل قسم، على طريقة Odoo. [التفاصيل أدناه](#لوحة-المهام--لماذا-لكل-قسم-مراحله).
- **دورة مهمة كاملة** — المدير يُسند، الموظف يسلّم ومعه المرفقات، المدير يعتمد ويقيّم. [docs/TASK_FLOW.md](docs/TASK_FLOW.md)
- **مساعد ذكي** — محادثة تقرأ بيانات المساحة الحيّة وتجيب بأرقام حقيقية. [كيف يعمل](docs/ASSISTANT.md)
- **Qodo Mail** — رسائل رسمية، وقنوات الأقسام، ومحادثات خاصة داخلية مع دخول اختياري بحساب Google وAI مساعد. [التفاصيل](docs/QODO_MAIL.md)
- **روابط دعوة ذاتية** — الموظف يفتح الرابط وينضم بحساب Google أو بكلمة مرور، ويظل الطلب بانتظار موافقة المدير.
- **بحث موحّد** — `Ctrl K` يبحث في التطبيقات والمهام والموظفين دفعة واحدة.
- **إشعارات على الهاتف** — عند إسناد مهمة، يصل إشعار حتى والمساحة مغلقة.
- **عربي وإنجليزي بالكامل** مع تبديل اتجاه الصفحة، وتعمل على الهاتف كما على الحاسوب.

الهوية والشعار من إنجوسوفت نفسها — ملفات الشعار الأصلية تُعرض كما هي دون أي تعديل.

## لوحة المهام — لماذا لكل قسم مراحله

بحثنا في طريقتين قبل التنفيذ:

| | Zoho Projects | Odoo Project |
| --- | --- | --- |
| النموذج | تخطيطات (Layouts) + حقول مخصصة + Blueprints لانتقالات الحالة | لكل مشروع مراحله الخاصة على لوحة Kanban |
| القوة | آلة حالات كاملة مع شروط وأتمتة | بساطة: أعمدة قابلة للترتيب لكل مشروع |
| التكلفة | يحتاج مسؤولاً يصمّم آلة الحالات قبل أن يُفتح أول طلب | لا شيء تقريباً |

**اخترنا نموذج Odoo.** فريق بحجم إنجوسوفت لا يحتاج آلة حالات، لكنه يحتاج بالتأكيد
ألّا يتظاهر خط مبيعات وطابور شكاوى بأنهما يتشاركان الأعمدة نفسها.

فلكل قسم مراحله ولونه وأيقونته:

| القسم | المراحل |
| --- | --- |
| المبيعات | عميل محتمل ← تم التواصل ← عرض سعر ← تفاوض ← تم الإغلاق |
| خدمة العملاء | واردة ← قيد المعالجة ← بانتظار العميل ← مُصعَّدة ← تم الحل |
| العمليات | جديدة ← مجدولة ← قيد التنفيذ ← تحت التدقيق ← مكتملة |
| التسويق | قيد الانتظار ← معتمدة ← قيد العمل ← قيد المراجعة / إعادة عمل / متوقفة ← منجزة |
| الموارد البشرية | طلب توظيف ← فرز ← مقابلات ← عرض وظيفي ← تم التعيين |
| التدريب | مقترحة ← إعداد المادة ← مجدولة ← تم التنفيذ |
| المالية | مطلوبة ← قيد المراجعة ← معتمدة ← تمت التسوية |
| تقنية المعلومات | بلاغ ← تشخيص ← قيد الإصلاح ← تأكيد الحل ← مغلقة |
| عام | لم تبدأ ← قيد التنفيذ ← قيد المراجعة ← منجزة |

الأقسام مأخوذة من أنظمة إنجوسوفت نفسها: `sales` و`operations` و`complaints` من
`DEPARTMENT_LABELS_AR` في لوحة تحليلات خدمة العملاء، والبقية من اللوحات الأخرى
ومن كون إنجوسوفت شركة تدريب.

**المشكلة التي يحلّها هذا التصميم:** لو كان لكل قسم أعمدته فقط، لتعذّر على أي شاشة
مشتركة — «أعمالي»، عدّادات الصفحة الرئيسية، ملخّص المساعد — أن تجمع المهام. لذلك
تُعلن كل مرحلة **نوعها المعياري** (`open` / `active` / `review` / `done`)، وهو ما
تتجمّع حوله تلك الشاشات. الأقسام تسمّي أعمدتها، والمساحة تظل تعرف معنى «منجزة».

التعريف كاملاً في [`shared/departments.js`](shared/departments.js).

### شجرة فريق التسويق

دور الصلاحية (`admin` / `manager` / `member` / `viewer`) منفصل عن الدور الوظيفي.
بهذا لا نضطر مثلاً إلى منح الـMedia Buyer صلاحيات مدير لمجرد أن هذا مسماه الوظيفي.

| الفريق الفرعي | الأدوار الوظيفية |
| --- | --- |
| الكرييتف | مصمم، مونتير فيديو، صانع محتوى |
| الماركتنج | سوشيال ميديا، أخصائي تسويق، أخصائي تسويق رقمي، منسق تسويق، منسق تسويق رقمي |
| الويب سايت | مدير تجارة إلكترونية، أخصائي تجارة إلكترونية، أخصائي SEO، مطور ويب |
| الميرشندايزنج | أخصائي ميرشندايزنج |
| البيرفورمانس | ميديا باير |

الموظف يرى لوحة قسمه فقط وتقييم مهامه هو فقط. المدير يرى مهام أعضاء قسمه وأداءهم
ويستطيع تصدير الجدول كملف CSV متوافق مع Excel وGoogle Sheets. مدير النظام وحده
يملك نطاق الشركة كلها.

عرض الجدول يحتوي: التاريخ، الفريق، المسند إليه، المهمة، الوصف، تاريخ التسليم،
الملاحظات، الحالة، عدد المرفقات، والتقييم من ٠ إلى ١٠٠. وبجانبه عرض الـKanban،
وطابور المراجعة، ونظرة الأداء.

### دورة حياة المهمة: إسناد ← قبول ← تنفيذ ← تسليم ← مراجعة ← تقييم

المهمة عقد بين شخصين، وتمرّ باتجاه واحد عبر **بوابتين**:

```
        ┌────────── المدير يُرجعها ومعها السبب ──────────┐
        ▼                                                │
   مُسندة ──▶ قبول الإسناد ──▶ قيد التنفيذ ──▶ بانتظار المراجعة ──▶ معتمدة
                                  │                   ▲
                                  └─ البوابة ١ ───────┘   البوابة ٢:
                                     مرفق + ملخص           المدير + تقييم من ١٠٠
```

- **المدير ينشئ المهمة** ويسندها لشخص واحد — ويصله إشعار. نموذج الإنشاء لا يحتوي
  خانة تقييم إطلاقاً، لأن العمل لم يبدأ.
- **الموظف يرد على الإسناد**: يقبل، أو يرفض مع سبب، أو يطلب توضيحاً، أو يقترح
  موعداً، أو يطلب إعادة الإسناد. لا يبدأ التنفيذ قبل القبول، وكل رد محفوظ في
  سجل مستقل.
- **البريف قابل للقياس**: لكل مهمة مرجع مقروء، وهدف، وتعريف واضح للإنجاز، ونقاط
  جهد، ووقت مقدر، ونسبة تقدم.
- **الموظف يسلّم** بعد أن يرفق ما أنجزه فعلاً. بدون مرفق لا تسليم.
- **المدير وحده يعتمد**، والاعتماد لا يتم بغير تقييم؛ أو يُرجعها ومعها سبب مكتوب.
- **سحب البطاقة لا يتجاوز بوابة.** إسقاطها على عمود مراجعة أو إنجاز يفتح البوابة
  المطلوبة بدل أن ينقلها، والـAPI يرفض الكتابة المباشرة على المرحلة في الحالتين.

الأداء صار يقيس **الاعتماد من أول مرة** و**عمق طابور المراجعة** و**مرات الإرجاع**
بجانب الالتزام بالموعد ومتوسط التقييم الموزون بنقاط الجهد.

التفاصيل الكاملة — البوابات، المرفقات، الصلاحيات، ومن أين جاءت القواعد —
في [docs/TASK_FLOW.md](docs/TASK_FLOW.md).

## التشغيل محلياً

```bash
npm install
npm run dev
```

يشغّل الاثنين معاً: الـ API على `:3000` والواجهة على **http://localhost:5174**.

في أول تشغيل يُنشئ الخادم حساب مدير النظام ويطبع كلمة المرور في الطرفية:

```
──────────────────────────────────────────────────────────
  Engosoft Workspace — first administrator created
  Email:    admin@engosoft.com
  Password: 8Kq2vN4pXm7dRt
──────────────────────────────────────────────────────────
```

تُعرض **مرة واحدة فقط**. غيّرها من قائمة الحساب بعد الدخول، أو حدّد
`ADMIN_PASSWORD` في `.env.local` قبل أول تشغيل.

نسخة الإنتاج محلياً:

```bash
npm run build
npm start          # http://localhost:3000
```

## متغيّرات البيئة

انسخ `.env.example` إلى `.env.local`. أهمها:

| المتغيّر | مطلوب؟ | ما هو |
| --- | --- | --- |
| `SESSION_SECRET` | في الإنتاج | يوقّع كوكي الجلسة. ٣٢ حرفاً عشوائياً. |
| `SSO_SECRET` | للدخول الموحّد | القيمة نفسها في التطبيقات التابعة. [docs/SSO.md](docs/SSO.md) |
| `DATABASE_URL` | مستحسن | Postgres. بدونه البيانات في ملف محلي. |
| `GOOGLE_CLIENT_ID` | اختياري | دخول الموظف بحساب Google المضاف مسبقاً؛ لا يمنح Qodo صلاحية Gmail. [docs/QODO_MAIL.md](docs/QODO_MAIL.md) |
| `OPENAI_API_KEY` | بديل اختياري | يستخدم OpenAI عندما لا تضبط خادم Qodo AI. [docs/ASSISTANT.md](docs/ASSISTANT.md) |
| `OPENAI_MODEL` | لا | افتراضياً `gpt-4o-mini`. |
| `QODO_AI_BASE_URL` | للموديل المدرّب | عنوان `/v1` لخادم OpenAI-compatible محلي أو مستضاف. عند ضبطه لا تحتاج OpenAI. |
| `QODO_AI_API_KEY` | حسب الخادم | مفتاح خادم Qodo AI إن كان يحمي الـendpoint. |
| `QODO_AI_MODEL` | لا | معرّف الموديل المرسل لخادم Qodo AI. |
| `MAIL_AI_MODEL` | لا | نموذج مستقل لأدوات Qodo Mail؛ يرجع إلى `QODO_AI_MODEL` ثم `OPENAI_MODEL`. |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` | لإشعارات الهاتف | `npx web-push generate-vapid-keys` |
| `ADMIN_EMAIL` / `ADMIN_PASSWORD` | لا | حساب المدير الأول. |
| `NODE_ENV=production` | في الإنتاج | كوكيز آمنة + رفض المفاتيح الناقصة. |

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

## إشعارات الهاتف

تعمل بمعيار Web Push: بعد توليد مفتاحَي VAPID ووضعهما في متغيّرات البيئة، يظهر
خيار **«تفعيل إشعارات الهاتف»** في قائمة الحساب.

```bash
npx web-push generate-vapid-keys
```

> **على الأيفون:** دعم Safari لإشعارات الويب موجود منذ iOS 16.4، **لكن بشرط
> إضافة الموقع إلى الشاشة الرئيسية أولاً** (شارك ← إضافة إلى الشاشة الرئيسية).
> في تبويب Safari عادي لا توجد الإمكانية أصلاً، ولذلك يخفي الخيار نفسه بدلاً من
> عرض زر لا يعمل. على أندرويد وسطح المكتب تعمل من المتصفح مباشرة.

## النشر على Railway

1. **New Project ← Deploy from GitHub** واختر هذا المستودع.
2. **+ New ← Database ← PostgreSQL** في المشروع نفسه.
3. في متغيّرات الخدمة:
   - `DATABASE_URL` = `${{Postgres.DATABASE_URL}}`
   - `SESSION_SECRET` و `SSO_SECRET` = قيم عشوائية
   - `QODO_AI_BASE_URL` و`QODO_AI_MODEL` لخادم Qodo المدرّب، أو `OPENAI_API_KEY` كبديل (اختياري)
   - `VAPID_PUBLIC_KEY` و `VAPID_PRIVATE_KEY` (اختياري)
   - `NODE_ENV` = `production`
4. `railway.json` يتكفّل بالباقي — البناء و`npm start` وفحص `/api/health`.

لنشر الموديل نفسه كخدمة Railway منفصلة، اتبع
[`ai/qodo-model/deploy/railway/README.md`](ai/qodo-model/deploy/railway/README.md).

> بدون `DATABASE_URL` يعمل التطبيق، لكن البيانات في ملف على قرص الحاوية — ويُمحى
> مع كل نشر جديد.

## الأدوار

| الدور | ماذا يستطيع |
| --- | --- |
| **مدير النظام** | كل شيء: المستخدمون، التطبيقات، الإعدادات، جميع المهام |
| **مدير** | يرى ويعدّل مهام قسمه، يرى أداء أعضاء القسم، ويصدّر الجدول |
| **موظف** | يرى لوحة قسمه، يعدّل مهامه، ويرى أداءه وتقييمه هو فقط |
| **مشاهدة فقط** | يفتح التطبيقات ويقرأ لوحة قسمه دون تعديل |

الدور يمنح مجموعة صلاحيات افتراضية، ويمكن تعديل أي صلاحية لمستخدم بمفرده من شاشة
التعديل. كما يمكن تحديد التطبيقات التي تظهر له في الشبكة.
