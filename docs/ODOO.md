# Odoo — the courses page

The workspace reads Engosoft's training out of Odoo 17 and shows it as
**الكورسات**. Read-only: courses are run in Odoo, and a second system quietly
editing them is how two sources of truth start disagreeing.

## Setup

Five variables. Without them the page says which ones are missing rather than
erroring, and the rest of the workspace is unaffected.

| Variable | What it is |
|---|---|
| `ODOO_URL` | `https://engosoft.com` — no trailing slash |
| `ODOO_DB` | `EngoSoft` |
| `ODOO_LOGIN` | The email of the account the API key belongs to |
| `ODOO_API_KEY` | Odoo → Preferences → Account Security → New API Key |
| `ODOO_UID` | Optional. Saves one authentication round trip after a restart |

The key inherits **that user's** permissions. A read-only Odoo account is the
right thing to point this at; nothing here writes, so nothing more is needed.

## What it reads

The custom module `lms_event_integration` extends Odoo's events into a course
catalogue. Three models matter:

| Model | Is | Fields used |
|---|---|---|
| `event.event` | a course | `code`, `name`, `date_begin`, `date_end`, `stage_id`, `event_type`, `attendance_method`, `if_offline`, `headquarter`, `instructor_id`, `total_lectures_number`, `session_duration`, `seats_taken`, `seats_max`, `address_id` |
| `event.track` | one lecture | `name`, `date`, `duration`, `event_id` |
| `event.stage` | the pipeline | `name`, `sequence`, `inprogress`, `pipe_end` |

Lectures are generated by the module from the course's lecture count and chosen
weekdays, and named `<course> / Session N`.

## Two things that will bite

**Odoo returns naive UTC.** `2026-08-06 06:00:00` carries no zone marker, so
`new Date()` in a browser reads it as local time and every lecture shows two
hours early in Cairo. `server/events.js` stamps them as UTC once, on the way
out, and nothing downstream has to remember.

**There are over a thousand courses.** Never query `event.event` unscoped.
Every query here is bounded by stage or date and capped, and the whole answer is
cached for a minute. Note also that the dotted domain `stage_id.inprogress` makes
Odoo join across the whole table and times out — resolve the stage ids first and
use `['stage_id', 'in', ids]`, which is what `coursesOverview` does.

## Checking it

`GET /api/events/status` answers whether the connection is configured and names
any missing variable. `POST /api/events/refresh` drops the cache.

Field discovery against the live database, when the customisation moves:

```bash
curl -s -X POST "$ODOO_URL/jsonrpc" -H 'Content-Type: application/json' -d '{
  "jsonrpc":"2.0","method":"call","params":{"service":"object","method":"execute_kw",
  "args":["'"$ODOO_DB"'", UID, "'"$ODOO_API_KEY"'", "event.event", "fields_get", [],
  {"attributes":["string","type","relation"]}]},"id":1}'
```

## Who sees it

Access is the app tile, not a new permission: an administrator ticks **الكورسات**
under Allowed apps on the user form. `server/routes/events.js` enforces the same
`canOpenApp` check the launcher draws with, so the tile and the API can never
disagree about who is allowed in.
